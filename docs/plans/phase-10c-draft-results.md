# Phase 10C draft persistence design

- Reuse Result (registration + examination + attempt + revision) and ResultItem (result + curriculum subject). Regular examinations use attempt 1; re-examinations require an APPROVED application for that exact registration/exam/subject and preserve its application attempt number, as explicitly confirmed. No replacement, carry-forward or grading policy is inferred.
- Add nullable ResultItem.status for ungraded drafts, Result.version for optimistic editing, a nullable unique ResultItem.reExamApplicationId link, and ResultDraftBatch for durable request/outcome idempotency. Existing rows retain their values. Null item outcomes must block transition to reviewed/approved/published records.
- Store only directly entered nullable decimal components and optional entered total; zero remains zero. Reuse Phase 10A component aliases and precision/max validators; block unknown component configurations or unconfigured component entries. Snapshot curriculum maxima in item sourceData, never calculate outcomes/GPA/grades.
- Recheck active enrollment, exact curriculum and period, exam context/lifecycle and application approval in a serializable transaction. Protect any existing non-DRAFT or previously published result; no revision generation in this phase. Lock drafts using their numeric version and audit previous/new values in the same transaction.
- Reuse owner-scoped Redis sources, mapping and fixed two-hour expiry. Produce a fresh import plan with created/skipped/rejected counts and a digest of source/context/current records; explicit confirmation submits that digest plus batch UUID. Commit revalidates inside the transaction. Changed plans return conflict; conflicting existing drafts are rejected and require manual editing, never silently overwritten. Identical existing subject marks are skipped. Updates count is always zero for Excel because no overwrite policy was approved.
- Record per-row outcome and audit batch UUID; durable unique batch UUID with actor/request digest prevents replay and divergent reuse. Serializable retries are bounded; atomic batch writes and audits roll back together. Recheck preview ownership/expiry immediately before completing writes.
- API permissions reuse results.read, results.write (create/edit) and imports.results.run plus results.write for draft import; no publish route. Staff-only accessible Results list/manual form and explicit import confirmation. Student endpoints remain unchanged.
- Before development migration: private pg_dump restored into isolated verification DB; table counts/content hashes verified. Test migration on isolated synthetic DB and preservation on restored copy. No real seeds/resets/MinIO changes. Current dev schema is untouched until these checks pass.
