# Authentication threat model (Phase 3)

Scope: staff authentication, sessions, CSRF and authorization in `apps/api` and `apps/web`.
Assets: staff sessions; the ability to publish results and issue/revoke certificates; staff credentials;
the audit trail.

| Threat                                                               | Mitigations                                                                                                                                                                                                                                                                                        | Residual risk / follow-up                                                                                                                                     |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Credential stuffing** (leaked password lists across many accounts) | Per-IP limit (100 / 15 min) counted before Argon2; per-account limit (20 / 15 min) across all IPs; password policy rejects common passwords; failures audited with hashed identifiers                                                                                                              | A botnet with many real IPs can still try ≤ 20 passwords per account per window. **MFA** is the real fix (future phase); optionally a breached-password check |
| **Brute-force against one account**                                  | 5 attempts / 15 min per account+IP, 20 per account; 12+ character passwords; Argon2id (19 MiB, t=2) makes offline cracking of a stolen hash expensive                                                                                                                                              | Per-account limit lets an attacker lock a user out for ≤ 15 min (deliberate trade-off vs. unlimited guessing); counters reset after a successful login        |
| **User enumeration**                                                 | Identical 401 body/code/message for unknown email, wrong password, disabled account and password-less account; unknown accounts still pay Argon2 (dummy hash); rate-limit responses identical for all emails; forgot-password answers identically (or 503 for everyone while mail is unconfigured) | Response timing is equalised for the hashing step, not network/DB jitter                                                                                      |
| **Session fixation**                                                 | New random session ID on every login; any session presented at login is revoked; IDs come only from the server                                                                                                                                                                                     | —                                                                                                                                                             |
| **Session theft** (XSS, logs, storage dumps)                         | Cookie is HttpOnly (+ Secure, `__Host-` in production); never in responses, URLs or logs (redaction + tests); Redis stores only `sha256(sessionId)`; 30 min idle / 12 h absolute lifetime; users can list and revoke sessions; password change/reset revokes sessions                              | A stolen live cookie works until expiry/revocation. Future: bind sessions to coarse client signals, MFA step-up for sensitive actions                         |
| **CSRF**                                                             | SameSite=Lax cookie; session-derived synchronizer token on every unsafe method; signed double-submit for login (login-CSRF) and reset; Origin allow-list check; CORS allow-list with credentials (no wildcard)                                                                                     | Relies on the web origin having no XSS (a same-origin script can fetch tokens) — CSP hardening is a later task                                                |
| **Disabled / removed accounts**                                      | Users are disabled, not deleted; status and roles are reloaded on every request; disabling revokes all sessions immediately; disabled accounts cannot log in (generic error)                                                                                                                       | —                                                                                                                                                             |
| **Privilege escalation**                                             | Central global guards; permissions from code-defined map; maker–checker separation tested; unknown role names grant nothing                                                                                                                                                                        | Role assignment UI/API arrives later and must require `users.manage`                                                                                          |
| **Proxy / IP spoofing**                                              | `TRUST_PROXY=true` is rejected; explicit trusted proxies only; the web edge proxy strips client-supplied `X-Forwarded-For`/`X-Real-IP` unless `WEB_BEHIND_TRUSTED_PROXY=true`; the per-account limit does not depend on IP                                                                         | Production must place the API behind the web server and configure TRUST_PROXY/LB correctly (documented)                                                       |
| **Redis outage**                                                     | Fail closed: sign-in and authenticated requests return 503; never treated as authenticated; `/health` reports it                                                                                                                                                                                   | Availability of admin features depends on Redis                                                                                                               |
| **Secrets in logs/audit**                                            | Structured logger redacts sensitive keys; access log excludes query strings; audit metadata redacted; login failures store HMAC hashes, not emails/IPs; tests scan captured logs for passwords, cookies and CSRF tokens                                                                            | Free-text log messages are not scanned — never interpolate secrets into messages                                                                              |
| **Password reset abuse**                                             | 256-bit single-use tokens, hash-only storage, 30 min TTL, new request invalidates old token, token in URL fragment, all sessions revoked on reset, rate-limited; no fake "email sent" while delivery is unconfigured                                                                               | Email channel security depends on the future mail provider                                                                                                    |
| **Default / weak admin credentials**                                 | No default users or passwords anywhere; `pnpm admin:create` enforces the policy and never echoes the password; e2e uses a random per-run password in a git-ignored file                                                                                                                            | —                                                                                                                                                             |
| **Configuration mistakes**                                           | Config validated at startup: production requires Secure cookies and a non-placeholder ≥32-char `SESSION_SECRET`; insecure cookies only for localhost                                                                                                                                               | Secret rotation invalidates CSRF tokens and identifier hashes (sessions survive) — document rotation runbook later                                            |

Out of scope for Phase 3 (planned): MFA, SSO/OAuth, CSP tightening, account lockout notifications,
admin user-management endpoints.

## Student portal (Phase 6)

| Threat                                                           | Mitigation                                                                                                                                 | Test                                           |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------- |
| Claiming someone else's account with a known registration number | Activation needs a single-use code issued to that registration; the number alone is never sufficient                                       | `activation.test.ts`                           |
| Guessing activation codes                                        | 60-bit codes; per-registration (5) and per-IP (30) throttling; the open code is revoked after 10 wrong guesses; codes expire (30 days)     | `activation.test.ts`                           |
| Learning which registrations exist / have codes                  | Identical `STUDENT_ACTIVATION_FAILED` / `AUTH_INVALID_CREDENTIALS` answers; unknown accounts still pay Argon2                              | `activation.test.ts`, `login-boundary.test.ts` |
| Database or log leak revealing codes                             | Only HMAC(SESSION_SECRET) of codes stored; codes never logged/audited; issuing response is `no-store`                                      | `activation.test.ts`, `admin.test.ts`          |
| Student escalating to staff, or staff acting as a student        | Separate principal, cookie, Redis namespace and guard; staff routes ignore the student cookie and vice versa; students have no permissions | `login-boundary.test.ts`                       |
| Reading another student's records                                | Student endpoints take no ids; data is derived from the session's student                                                                  | `login-boundary.test.ts`                       |
| CSRF on student actions                                          | Same session-HMAC / pre-auth double-submit scheme; staff tokens do not validate student sessions                                           | `login-boundary.test.ts`                       |
| Compromised student account                                      | Staff lock/disable ends all sessions at once; recovery code resets the password and ends sessions                                          | `login-boundary.test.ts`, `activation.test.ts` |

Open: code delivery channel and identity check at hand-over are university procedures (client decision).
